# ライティングガイド {/* #writing-guide */}

このサイトは「人」のために書かれています。コードベースのためではありません。コードは常に変わりますが、ここに書かれるのは安定したものだけ——製品とは何か、概念が何を意味するか、ワークフローがどう見えるか——であり、ファイルやシンボル、行番号を引用することはありません。執筆中に事実をリポジトリで確認することはありますが、読者がリポジトリを必要とすることはありません。

## ドキュメントの原則 {/* #principles */}

これらの規則は文体より上位にあります。コードが変わり続ける間も、このサイトを正しく保つのはこれらです。

次のことは決してしません：

1. コードからドキュメントを参照する——ソースファイルのコメント・メッセージ・識別子は、ドキュメント名・節番号・記録番号を決して名指ししません。コメントが説明するのはコードそのものです；
2. サイトにソース上の位置を書く——ファイルパス、シンボル名、行番号、「ソースを参照」の類のリンクをどのページにも置きません；
3. リポジトリ外のファイルをサイトから参照する——調査ノート、ローカルのアーカイブ、草稿は公開ページに流し込みません；
4. プロセスの痕跡を残す——タスク番号、レビュー回、プローブ ID、検収の言い回しを書きません。ページは事実を述べ、それを生んだ過程は述べません；
5. 実装コードを真実として貼る——例に出すのはコマンド・設定・出力だけ。実装内部の断片はコピーしません；
6. 一つの事実に二つの出所を置く——用語は `terminology.yaml`、コマンドの面は CLI リファレンス、生成ページは生成器から。写しと出所が食い違ったら出所が勝ちます；
7. 決定を独立した番号付きの記録に切り出す——ADR（アーキテクチャ決定記録）などの形態は知識を断片化し、文脈から離れて腐ります。決定はそれが効く場所に、理由とトレードオフごと、流れの中で書きます。

次のことは明示的に許されます：

1. 製品の挙動を完全に記述する——コマンド、設定、ワークフロー、意味。それがこのサイトの役目です；
2. 執筆中に事実をリポジトリで確認する——本文にパスを書かないことと、確認することは両立します；
3. サイトをコードと同じリポジトリ・ブランチ・レビューの流れに置く；
4. コード内の API ドキュメントはそれぞれの読者に仕える——サイトとコードのドキュメントは独立して成立します；
5. コンポーネントを平易な言葉で呼ぶ——取り込み、保存、検索、コンテキスト、検証——図でも同じく。何をするかを言い、どこに住むかは言いません。

意図的に閉じている例外が一つあります：将来、貢献者向けのセクションが他プロジェクトの開発者ガイドのようにコードを引用できるようになるかもしれません。このスイッチは明示的な決定によってのみ開きます——ページが独断でそちらへ流れることはありません。

## 言語 {/* #languages */}

- 英語が既定のロケールで、簡体字中国語（`zh-CN`）と日本語（`ja`）は対等です。すべてのロケールはそれぞれのパスの下に住み、どの言語もサイトのルートを取りません。
- 執筆は中国語で起草します。英語と日本語のページは完成した中国語の草稿から作られます——まず機械による初回パス、次に自然に読めるための編集パス——配置されたあとは対等に扱います。
- ページは先に英語で公開されてもかまいません。未訳のページは英語にフォールバックし、マイルストーン（リリースなど）までに全言語が揃います。

## ページ契約 {/* #page-contract */}

すべてのページは：

1. そのページが何のためのものかを一文で述べる冒頭から始まります；
2. front matter に `description` を持ちます——一文、最大 150 文字。検索結果と機械可読インデックスに表示されるのはこれです；
3. すべての見出しに明示的な ID（`## タイトル {/* #an-id */}`）を付けます。さもないと翻訳が自動生成のアンカーを変え、既存のリンクを壊します；
4. 一つのアイデアだけを扱います。二つの問いに答えるページは二つのページです；
5. 前提条件がある場合は、最初の手順の前に明記します；
6. front matter に `type:` を宣言します——`concept`、`task`、`reference`、`troubleshooting`、`meta`。

## 語調と文体 {/* #voice */}

英語ページは Google の開発者向けドキュメント スタイルガイドの会話調・二人称・能動態・現在時制に従います——読者を *you* と呼び、条件を指示より先に置き（"To delete a project, …"）、文は短く、見出しはセンテンスケース、リンクテキストは常にリンク先を説明し、"click here" は使いません。

中国語ページは中国語技術文書の慣例に従います——中国語と欧文・数字の間にスペース、中国語の文内は全角句読点、製品名の大文字小文字は正しく（`Momotaro`、`GitHub`、`SQLite`）、約物の重ね打ちはしません。これらの規則は lint ステップが CI に入ったあと、zhlint と autocorrect が機械的に確認します。

日本語ページも同じ原則に従います。最初の日本語コンテンツが入るとき、同じ「機械の初回パス + 編集パス」の二段階を通します。

## アクセシビリティ {/* #accessibility */}

- 情報を伝える画像には、見た目ではなく「何を伝えるか」を書いた alt テキストを付けます。装飾のみの画像は `alt=""` です。
- alt テキストは 150 文字以内に収め、「画像」で始めません。
- 構造は見出しで表現し、太字で代用しません。見出しレベルは飛ばしません。
- 方向だけに頼る表現（「上記」「右側」）は使いません——名前かリスト内の位置で示します。
- `and` は語として書き、`+` で代用しません。スクリーンリーダーは記号を読み上げられません。

## 図 {/* #diagrams */}

- 図はテキスト（Mermaid）で書き、他の内容と同じようにページに住み、ページと一緒に翻訳されます。
- すべての図はタイトル（`accTitle`）と説明（`accDescr`）を支援技術の読者のために持ち、隣の文が何を示すかを述べます——図をすべて飛ばしてもページは完全に読めなければなりません。
- 図はノード 10 個未満に保ちます。ラベルはこのサイトの語彙から——平易な部品名——ファイル名・シンボル名・コードの略記は決して使いません。
- 図は場所を稼いだときだけ加えます。文章が本当に描いて見る必要のある構造・流れ・ライフサイクルだけです。

## 用語 {/* #terminology */}

- 用語の唯一の情報源は `terminology.yaml` です。用語集のページはそこから生成されます。一度名前を付けた概念に二つ目の言い方を導入してはいけません——一つの語を選び、どこでもそれを使います。
- 用語がページに最初に現れるとき、用語集へリンクします。
- 同じ概念に複数の一般的な表記がある場合、`terminology.yaml` が決めます。決定は書き留め、ページごとに議論し直しません。

## 翻訳しやすく書く {/* #translation-friendly */}

明示的な見出し ID に加えて：慣用句・文化的な典故・ユーモア・季節の例を避け、日付と単位は曖昧さなく書き、一文には一つの指示だけを載せます。これらの規則は、中国語の草稿・英語のページ・日本語のページを同じチェックリストでレビューできるようにするためのものです。

## コードコメントと命名 {/* #comments */}

ソースファイルはページと同じ執筆規律に従います。

### 命名 {/* #names */}

識別子——モジュール、型、関数、定数、変数、テスト、フィクスチャ——はバージョンのコードネームを決して持ちません。バージョン番号は値としてのみ存在します：ワイヤ表記、定数、移行ステップの番号、ファイル名テンプレート。歴史的な成果物の名前がどうしてもスキーマのバージョンに触れる必要があるときは、バージョンを書き下します——`…_at_schema_2`、`…_v2_…` にはしません。プロセスの番号（波、レビュー回）はコードにまったく入りません：識別子・コメント・テストメッセージは事実を運び、どこで起きたかは運びません。

### コメント {/* #comment-rules */}

1. 読者で層を分けます：呼び出し側が見える契約は `///` ドキュメントコメント（クレート／モジュールの先頭は `//!`）；実装の動機・トレードオフ・不変条件は `//` で、API ドキュメントには決して描画されません。
2. なぜを説明し、コードを翻訳しません。型システムが既に語っていることを繰り返しません。ドキュメントコメントの冒頭の一行は要約で、200 文字以内です。
3. ドキュメントの節はシグネチャに対応します：`Result` を返すものは `# Errors`（どのケース、どのエラー）、panic しうるものは `# Panics`、`unsafe fn` は `# Safety`（呼び出し側の義務を箇条書きで）、まとまった用法があるものは `# Examples`（例では `?` を使い、定型行は `#` で隠します）。
4. すべての `unsafe {}` ブロックの直前に `// SAFETY:` を置き、この箇所が契約の各義務をなぜ満たすかを書きます。
5. 禁止：コメントアウトされたコード；`/* … */` のバナー（本当に区切りが必要なときは `////`）；シグネチャ行内のコメント；`//` 内の `#` 見出し；空のドキュメントコメントと、その直後のぶら下がった空行。
6. コメントはドキュメントを決して引用しません——`§`、ドキュメント名、記録番号を出さず——タスクやレビューの番号も運びません。事実はそれが生きる場所に書きます：ドキュメントは再編され、参照は腐ります。
7. バージョンはコメントでも命名と同じに振る舞います：値としてのみ、コードネームとしては決して。`schema 3` と書き、`v3` とは書きません。
8. `TODO` と `FIXME` は `// TODO(#<issue>, <担当者>): 事項` の形にのみ存在します；追跡元のないものは他所に登録し、コードに長く居座らせません。
9. リンクと行幅：ドキュメントコメント内のコードは `[Item]`、外部 URL は `<https://…>`；行幅は 100 列以内；クレートの根は `rustdoc::all` と `rustdoc::unescaped_backticks` の警告を有効にします。

## レビューとツール {/* #review */}

- 中国語ページは zhlint と autocorrect、英語ページは英語の編集が始まってから Vale（Google スタイルパッケージ + プロジェクト語彙）が確認します。チェックは CI に入ります——まず非ブロッキングの警告として導入し、ノイズを調整してからブロッキングに昇格します。
- `description` の要件はビルド自体が守ります。欠落または長すぎる場合はビルドが失敗します。
- ページが完成したと言える条件：ビルドを通り、配置されたすべての言語で自然に読め、少なくとも一人のレビュアーが手順を一度たどっていること。
