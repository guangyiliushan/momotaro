# 写作规范 {/* #writing-guide */}

本站在为「人」写作，而不是为代码库写作。代码时刻在变；这里只描述稳定的东西——产品是什么、概念意味着什么、工作流程长什么样——并且从不引用文件、符号或行号。写作过程中事实可以回仓库核对，但读者理解任何一页都不需要仓库。

## 文档原则 {/* #principles */}

这些规则高于文风。它们让本站保持正确——即便代码持续变动。

以下事情坚决不做：

1. 代码引用文档——源码文件的注释、消息与标识符绝不出现文档名、章节号或记录编号；注释解释的就是代码本身；
2. 站点出现源码位置——任何页面都不写文件路径、符号名、行号或"见源码"式链接；
3. 站点引用仓库外的文件——研究笔记、本地存档与草稿不进入已发布页面；
4. 留下过程痕迹——不写任务编号、评审轮次、探针编号或验收语汇；页面陈述事实，不陈述产生它的过程；
5. 把实现代码当真相照贴——示例只给命令、配置与输出，不复制实现内部的片段；
6. 同一事实留两处来源——术语来自 `terminology.yaml`、命令面来自 CLI 参考、生成页来自其生成器；副本与来源冲突时以来源为准；
7. 把决策拆成独立的编号记录——ADR（架构决策记录）这类形态会把知识切碎、脱离语境并腐化；决策写进它生效的地方，连同理由与取舍，融进叙述。

以下事情明确允许：

1. 完整描述产品行为——命令、配置、流程、语义：这正是本站的职责；
2. 写作时回仓库核对事实——文中永远不写路径，但这不影响核对；
3. 站点与代码同仓库、同分支、同评审流；
4. 代码内的 API 文档服务各自的读者——站点与代码文档彼此独立、各自成立；
5. 用平实词汇称呼组件——摄取、存储、检索、上下文、引用校验——图里也一样：说组件做什么，不说它住在哪。

有一个例外有意保持关闭：未来面向贡献者的栏目，可以像其他项目的开发者指南那样引用代码。这个开关只能由显式决定打开——任何页面不得自行漂移过去。

## 语言 {/* #languages */}

- 英文是默认语言；简体中文（`zh-CN`）与日文（`ja`）是对等的语言：每种语言都住在自己的路径段下，没有任何语言占据站点根。
- 写作以中文起草。英文页与日文页由定稿中文产出——先过一遍机器初翻，再过一遍人工编辑使其读起来自然——落位后与中文同等对待。
- 页面允许先落英文。缺失的译文回落到英文，直到某个里程碑（例如一次发布）要求全语种齐备。

## 页面契约 {/* #page-contract */}

每篇页面：

1. 以一句话开头，说明这一页是干什么的；
2. front matter 必带 `description`——一句话、至多 150 字符；搜索结果与机器可读索引展示的就是它；
3. 每个标题都带显式 ID（`## 标题 {/* #an-id */}`），否则翻译会改变自动生成的锚点、拆掉既有链接；
4. 一页只讲一件事；回答两个问题的页面就是两个页面；
5. 有前置条件时，在第一步之前先写明；
6. 在 front matter 声明 `type:`——`concept`、`task`、`reference`、`troubleshooting` 或 `meta`。

## 语气与文风 {/* #voice */}

英文页遵循 Google 开发者文档风格指南的基调：对话式、第二人称、主动语态、现在时——直接称呼读者为 *you*，条件先于指令（"To delete a project, …"），句子求短，标题用句子式大小写，链接文字永远描述目标、不用 "click here"。每页的开篇一句不超过 200 字符。

中文页遵循中文技术写作的通行规范：中文与西文/数字之间加空格、中文句内使用全角标点、产品名保持正确大小写（`Momotaro`、`GitHub`、`SQLite`）、不叠用标点。这些规则在 lint 步骤进 CI 后由 zhlint 与 autocorrect 机器把关。

日文页遵循同样的原则；第一批日文内容落地时，同样"机器初翻 + 人工编辑"两道工序。

## 无障碍 {/* #accessibility */}

- 有信息量的图片都配 alt 文本，描述图片*传达什么*而不是长什么样；纯装饰图用 `alt=""`。
- alt 文本不超过 150 字符，不以"图片"开头。
- 层级一律用标题表达，不用加粗代替；标题级别不跳级。
- 不写只靠方位的表述（"上面"、"右侧"）：用名字或"列表中的第几项"指代。
- `and` 写成词，不写 `+`；屏幕阅读器读不了符号。

## 图表 {/* #diagrams */}

- 图用文本（Mermaid）写，与页面其他内容同住，随页面一起翻译。
- 每张图都带标题（`accTitle`）与描述（`accDescr`），供使用辅助技术的读者使用；图旁的句子说明它画了什么——把图全部跳过后，页面仍要能完整读懂。
- 一张图保持在十个节点以内。标签取自本站词汇——平实的组件名——绝不出现文件名、符号名或代码简写。
- 只有挣得位置才加图：文字确实需要看见的结构、流程或生命周期。

## 术语 {/* #terminology */}

- 术语的唯一来源是 `terminology.yaml`；术语表页由它生成。一个概念一旦定名，绝不引入第二种说法——选定一个词，处处用它。
- 术语在页面上第一次出现时链接到术语表。
- 中文里一个概念有多种常用写法时，由 `terminology.yaml` 拍板；把决定写下来，不要每页重吵一遍。

## 为翻译而写 {/* #translation-friendly */}

除显式标题 ID 之外：避免成语、文化典故、幽默与季节性例子；日期与单位写法无歧义；一句话只承载一个指令。这些规则的目的是让中文草稿、英文页与日文页能用同一张检查清单来审。

## 代码注释与命名 {/* #comments */}

源码文件遵守与页面相同的写作纪律。

### 命名 {/* #names */}

标识符——模块、类型、函数、常量、变量、测试、夹具——绝不携带版本代号。版本号只作为值存在：线格拼写、常量、迁移步编号、文件名模板。历史制品确实需要在名字里提到某个 schema 版本时，把版本写全——`…_at_schema_2`，不写 `…_v2_…`。过程编号（波次、评审轮次）根本不进代码：标识符、注释与测试消息携带事实，不携带它发生在哪一步。

### 注释 {/* #comment-rules */}

1. 按读者分层：调用者看到的契约写 `///` 文档注释（crate / 模块头部用 `//!`）；实现动机、取舍与不变量写 `//`，它绝不渲染进 API 文档。
2. 解释为什么，绝不翻译代码；类型系统已经表达的不再复述。文档注释的开头一行是一句话摘要，不超过 200 字符。
3. 文档段与签名配套：返回 `Result` 的写 `# Errors`（哪种情形、哪个错误）、可能 panic 的写 `# Panics`、`unsafe fn` 写 `# Safety` 并逐条列调用者义务、有成套用法的给 `# Examples`（示例用 `?`、样板行用 `#` 隐藏）。
4. 每个 `unsafe {}` 块之前写 `// SAFETY:`，说明此处为何满足契约施加的每一项义务。
5. 禁止：注释掉的代码；`/* … */` 横幅（确要分隔用 `////`）；签名行内注释；`//` 注释里的 `#` 标题；空文档注释及其后的悬挂空行。
6. 注释绝不引用文档——不出现 `§`、文档名或记录编号——也不携带任务与评审编号。事实写进它所在的地方：文档会重排，引用会烂。
7. 版本在注释里的行为与命名一致：只作为值，绝不做代号。写 `schema 3`，不写 `v3`。
8. `TODO` 与 `FIXME` 只以 `// TODO(#<issue>, <责任人>): 事项` 存在；没有跟踪来源的登记到别处，绝不长期停在代码里。
9. 链接与行宽：文档注释里引用代码写 `[Item]`、外部 URL 写 `<https://…>`；行宽不超过 100 列；crate 根开启 `rustdoc::all` 与 `rustdoc::unescaped_backticks` 告警。

## 评审与工具 {/* #review */}

- 中文页由 zhlint 与 autocorrect 检查；英文页在英文编辑阶段起由 Vale（Google 风格包 + 项目词表）检查。检查进 CI——先以非阻塞告警放行、调低噪声后再升为阻塞。
- `description` 要求由构建本身把关；缺失或超长会构建失败。
- 一页算完成的标志：过了构建、每种落位的语言读起来都自然、且至少有一位评审人把步骤走过一遍。
